# srs-integ

A black-box integration suite for the SRS media server. It tests features and
interfaces from outside the process, only through what a client, an operator or
a callback server can see, so a rewritten server could pass the same cases.

It is its own Go module, `srs-integ`, separate from the root `srsx` module. It
imports no package of the repository, only its own packages and third-party
modules, and needs no cgo.

## Run

From the repository root:

```bash
make integ          # The test media, then every case: the timer cases and the others, as two go test processes at once.
make integ-prepare  # Only the test media.
make bin/srs-integ  # The CLI, also built by make build.
```

One feature or one case:

```bash
go -C cmd/integ/cases test -count=1 -run 'Test(Timer_)?Hls_'
go -C cmd/integ/cases test -count=1 -run 'TestRtmp_Common/PlayBeforePublish'
```

The cases run `trunk/objs/srs`, built with every feature the suite needs, and
fail with "rebuild it ..." when `/api/v1/features` lacks one:

```bash
cd trunk && ./configure --srt=on --gb28181=on --rtsp=on --utest=on --sanitizer=on --ffmpeg-opus=off --simulator=on && make
```

Flags, after `-args`:

- `-integ.srs <path>`: another SRS binary.
- `-integ.timer`: allocate ports from the timer process's part of the range; `make integ` sets it for the timer process.
- `-integ.known-bugs fail`: known-bug cases fail like normal cases; the default, `pass`, lets a known bug that fails pass.
- `-integ.scale N`: run each case N times as separate cases, named `<Case>`, `<Case>-2` to `<Case>-N`, each with its own stream on its group's server; timer cases run once, since each starts a server of its own. The scale check.
- `-integ.shards K`: split Common into K identical servers; a case gets the one its name picks. The default is 4: every case starts at once, and one single-threaded Common made the slowest real-time cases miss their 500ms limit while it was saturated in the first part of a run; 2 held until the HLS cases added their bursts, 3 until the suite had about 1,300 cases (Common cases at 570-600ms in a fast run).
- `-integ.settle D`: start the Fast and Normal cases no earlier than D after the process starts; timer cases start at once. `make integ` sets 2s for the timer process: it starts every case at once, beside the main process's first cases, and its few short cases missed their limit in that burst (up to 670ms for cases of 110ms alone). Its 5s timer cases set its run time, so the wait costs nothing.
- `-integ.limit-scale F`: multiply every class limit by F, at least 1, and the time the hook, security, edge and forward cases wait for SRS to accept or refuse a client. CI runs with 4: its runners are slower and have fewer cores, and a case that hangs still fails.

`make integ`, `make integ-main` and `make integ-timer` pass `INTEG_ARGS` after
`-args`. The scale check runs about 1,000 cases:

```bash
make integ-main INTEG_ARGS="-integ.scale=56"
```

CI runs the suite in the `trunk/Dockerfile.test` image, as the `test` job of
`.github/workflows/test.yml` does:

```bash
docker build --tag srs:test -f trunk/Dockerfile.test .
docker run --rm -w /srs --env FFMPEG=/usr/local/bin/ffmpeg7 srs:test make integ INTEG_ARGS=-integ.limit-scale=4
```

The image's `ffmpeg` is 5.0, which writes HEVC in FLV the legacy way, so the
test media comes from its `ffmpeg7`; it has no VP9 or AV1 encoder, so those
cases skip. The Linux-only cases, such as the `/proc` values of the API, run
there.

Each `go test` process ends with its summary: the cases passed, failed and
skipped with their reasons, the known bugs, and the 10 slowest cases. Then the
SRS processes it started and the most that ran at once, the ports it took, and
the CPU each Common server used, as a share of the one core SRS runs on. Run it in
`cmd/integ/cases` with no package argument, as above, or `go test` hides the
summary of a passing run.

Each run works in `/tmp/srs-integ/<pid>/`, one directory per server with its
env, pid file and console log. A group's directory is removed when it passes
and kept when it fails; a failing case shows the last 30 lines of the log. The
run removes its directory when every test passed, and the directories of
earlier runs whose process is gone.

The CLI gives the stream tools by hand:

```bash
bin/srs-integ probe <url>            # Print the stream report of rtmp://, rtmps://, http://...{flv,ts,aac,mp3,m3u8,mpd}, a WHEP URL (http://host:1985/rtc/v1/whep/?app=live&stream=s, offering every codec), srt://host:port?streamid=#!::r=live/s,m=request (also passphrase, pbkeylen and latency in ms), rtsp://host:port/app/stream (over TCP) or an FLV, TS, AAC, MP3 or MP4 file; -duration, -timeout.
bin/srs-integ publish <file> <url>   # Publish an FLV file in real time, to rtmp:// or rtmps://, or an MP4 file with H.264, HEVC, VP9 or AV1 and Opus by WHIP (http://host:1985/rtc/v1/whip/?app=live&stream=s; it adds vcodec for a codec other than H.264), or an MPEG-TS file to srt://host:port?streamid=#!::r=live/s,m=publish, timed by its PCR. Neither verifies an rtmps:// certificate, like ffmpeg.
bin/srs-integ prepare -h             # Make the test media; its flags.
```

## Layout

- `main.go`: the CLI.
- `internal/server/`: the adapter, the only package that knows the SRS binary, its env var names, its ports and its paths.
- `internal/media/`: the test media: its recipes, the prepare cache, and FLV and MP4 readers, with the protection (`sinf`) of encrypted MP4 tracks.
- `internal/rtmp/`: the RTMP client: the simple and complex handshakes, chunk sizes, connect options, FMLE and Flash publish, play, FLV tags in and out including enhanced RTMP, real-time pacing, and RTMPS (`Options.TLS`, `Client.TLS`).
- `internal/report/`: the stream report every analyzer fills, and `Until`, the stop condition a case states.
- `internal/httpplay/`: the HTTP stream player the FLV, TS and audio players share: it sends its own method, Host and headers, and waits for the answer and each unit its decoder reads with a deadline.
- `internal/flv/`: the FLV analyzer, and the RTMP and HTTP-FLV players that feed it; `HTTPPlayer` also waits for the FLV header flags. HEVC in legacy tags, codec id 12, is an error unless the analyzer has `LegacyHEVC`, so a server that sends it instead of enhanced RTMP fails the cases.
- `internal/ts/`: the TS demuxer (PAT, PMT, PES; H.264, HEVC, AAC, MP3 and Opus; each PES with the codecs of its PMT), its analyzer, and the HTTP-TS players.
- `internal/audio/`: the ADTS and MP3 frame readers, the raw .aac and .mp3 analyzer, and its HTTP players.
- `internal/mp4/`: the fragmented MP4 reader (init, moof and mdat) and the analyzer of MP4 samples, for HLS fmp4, DASH and MP4 files, progressive or fragmented.
- `internal/hls/`: the m3u8 parser (master and media playlists, keys, init maps) and the HLS player: TS or fmp4 segments, AES-128 decryption (`hls.Decrypt` for one segment), live playlists.
- `internal/dash/`: the MPD parser (segment templates and timelines) and the DASH player, which merges the video and audio representations in time order.
- `internal/rtc/`: the WebRTC client, built on pion: a WHIP publisher of samples read from an MP4 file (H.264, HEVC, VP9 or AV1, and Opus) or a raw G.711 file, and a WHEP player, or both by SRS's legacy JSON API; each session offers H.264 and Opus or the codecs of its options, none of a kind whose list is empty, and a publisher's track sends the codec SRS chose; `Options.SenderReports` makes a publisher send its own Sender Reports from the decode times of its samples, two before a track's first packet, in place of pion's once a second of wall time, and `Options.AudioReportShift` moves the audio's later; `WithoutSEI` drops the SEI NALs of H.264 and HEVC samples; ICE over UDP on the loopback interface, checked every 20ms rather than pion's 200ms, or with `Options.TCP` only over TCP, from pion's active TCP candidates to the server's passive one (RFC 6544); `Options.Setup` posts an offer with the DTLS setup active or passive in place of actpass; `Transport` tells whether ICE selected a UDP or a TCP pair; `Delete` of the session's Location; the publisher counts the PLIs SRS sends, and the player sends one with `RequestKeyframe`; the analyzer rebuilds H.264 and HEVC frames from RTP for the TS analyzer, VP9 frames (keyframe, profile and size from the uncompressed header) and AV1 temporal units (the sequence header's profile and size, the frame header's type), and counts each Opus or G.711 packet. `Offer` makes an offer of chosen codecs and `Post` sends it without connecting, to check an answer or an error status. A raw publisher and player, without a peer connection, for `encrypt=false` and `dtls=false`: one STUN binding to the answer's UDP candidate, or its TCP one with each packet framed as RFC 4571 says, the DTLS handshake with pion/dtls or none, then RTP and RTCP in clear; `Abort` closes its socket without a DTLS alert. `Bind` sends the binding requests of a session's offer and answer from a new UDP or TCP socket, as an ICE-controlling or controlled agent, and returns the address the server saw, `ErrClosed` when it closes the connection, or the deadline. Each session has a `Recorder`, the interceptor under pion's, which logs the RTP and RTCP as the network carries them: for each stream by SSRC, the sequence numbers a later packet skipped (`Missed`), those that came after (`Late`), those that came or were sent again (`Repeated`), and an RTX stream's original sequence numbers (`OSNs`); the RTCP packets each way, read with `Nacked` and `TWCCFeedback`; and the transport-wide sequence numbers sent. pion's NACK generator asks every 20ms rather than 100ms, at most 10 times for a packet. `Options.RTX` offers RTX (RFC 4588) for each video codec, payload type plus one, and `Options.TWCC` makes a publisher send the transport-wide sequence number. `Username` is the session's name in SRS, the server's ICE ufrag and the client's.
- `internal/srt/`: the SRT client, a caller built on the pure-Go gosrt (checked against libsrt by its unit tests, with ffmpeg as the listener both ways): `Dial` with the streamid, passphrase, key length and latency of `Options` (`ParseURL` reads them from an srt:// URL); a refused handshake is a `RejectError` with libsrt's reason, such as 1010 for a wrong passphrase and 1011 for a missing or unexpected one; `WaitClosed` reads until the server closes, and `WaitClosedProbing`, for a caller dialed with a short `PeerIdleTimeout`, also sends a null TS packet now and then, so a server that closed without the client hearing it (gosrt drops a shutdown that comes while its `Dial` returns) ends the connection by its silence; `TSBPD` is the delay each end holds what it receives, from the handshake; `Analyze` and `Play` feed the TS a player gets to the TS analyzer. `Sender` sends a TS file in messages of 7 packets, each timed by its latest PCR: `SendThrough` sends the start at once, `Stream` the rest in real time.
- `internal/rtsp/`: the RTSP player, built on gortsplib: `Play` sends DESCRIBE, SETUP of every media over TCP (interleaved) or, with `Options.TryUDP`, over UDP first and then TCP when the server refuses it, and PLAY; a refused request is a `StatusError` with its method and status; the analyzer rebuilds H.264 and HEVC frames from RTP, as the WebRTC one does, and reads the AAC frames of RFC 3640 packets with the config of the SDP, which it counts as the audio sequence header. HEVC with a payload type outside the dynamic range, which gortsplib leaves generic, is known by its rtpmap. `Conn` is a raw connection that sends a request as it is given, with the next CSeq, reads its answer past the interleaved frames, and counts them; `ReadFrames` counts the frames for a while, and `WaitClosed` reads until the server closes.
- `internal/gb/`: the GB28181 media publisher, without SIP, as an external SIP server drives a device: `Publish` asks for a session by the publish API (`/gb/v1/publish/`, the SSRC in 10 digits) and `Post` sends a body as it is; `ReadFLV` turns an H.264 or HEVC and AAC FLV file into frames, Annex B with the parameter sets before each keyframe and ADTS; the `Muxer` makes a PS pack of each frame (the pack header, the system header and stream map before each keyframe, PES packets of at most 65,535 bytes), checked against ffmpeg's PS demuxer by its unit tests; the `Publisher` sends each pack in RTP packets of at most 1,400 bytes over TCP, each after its length (RFC 4571), paced like the RTMP publisher, and raw RTP packets or frames for bad input.
- `internal/metrics/`: a strict parser of the Prometheus text format, so a case sees what a scraper reads: each family with its HELP, TYPE and samples, and the label values with their escapes; a malformed line is an error.
- `internal/mock/`: the HTTP server SRS calls back, for the hooks, the heartbeat and the forward backend: it records every request (method, path, query, headers, body and its JSON) and answers by script (ok, a reject code, an HTTP error, a delay, no answer, or any JSON), routed by action and stream; `Wait` blocks until a request that matches arrives.
- `internal/check/`: the case helper.
- `cases/`: the cases.
- `testdata/`: the self-signed TLS key and certificate of the TLS listeners, for localhost and 127.0.0.1, test-only; the generated media goes in `testdata/media/`, which git ignores.

Each internal package has its own unit tests.

## Rules

### Black box

A case observes SRS only through the network (RTMP, HTTP, WebRTC, SRT, RTSP,
UDP), the HTTP API and the callbacks it sends, the files it writes, its exit
code and the signals the case sends it. No SRS source, internals or log text
decides pass or fail; the log is attached only to explain a failure. The
cases of the log settings (`TestEnv_*`) and of the log's reopen
(`TestTimer_Signal_LogFile`, `TestTimer_Signal_Console`) are the one
exception: the log is what those settings and that signal change, so they
read where it goes and the header of each line, its time, level and pid,
never its text.

### Env only

SRS starts as `objs/srs -e` with `SRS_*` env vars, never with a config file. A
feature that needs a file, such as several vhosts, gets no case.

### Naming

- **Normal cases:** `Test<Feature>_<Group>/<Case>`, such as `TestRtmp_Common/PlayBeforePublish`.
- **Timer cases:** `TestTimer_<Feature>_<Group>/<Case>`, such as `TestTimer_Hls_Dispose/FilesRemoved`.
- **Group:** `Common`, the one shared server with every feature on, or the name of a variant server.
- **Feature:** one name per feature area, such as `Rtmp`, `HttpFlv`, `Hls`, `Rtc`, `Api` or `Hooks`. Reuse a name from the catalog before adding one.

`make integ` runs `^TestTimer_` in one process and everything else in another,
with `-parallel 24`, at the same time. With 64 cases at once, the cases that
start together slowed each other past their limit, while the run took no
less time; with 32, at about 1,300 cases, a fast run still had cases at
500-600ms, and 24 holds them under 420ms in about the same time.

### Servers

- **Common:** one SRS with every feature that doesn't change how other streams behave, started by the first case that uses it and stopped after every test ends. Each case uses its own stream name. It runs as 4 identical shards by default (`-integ.shards`), and a case's name picks its shard, so every `server.Common(c)` of a case is the same server.
  Its listeners: RTMP, RTMPS, the HTTP API and server, HTTPS for both, WebRTC over UDP and TCP, SRT, RTSP, the exporter, and the GB28181 media port. The MPEG-TS over UDP caster needs a variant, `TestCaster_UdpTs`, because a server has one stream caster. RTMP also listens on `[::]` on the same port (`Config.IPv6`), when the host has IPv6.
  Its TLS listeners use the self-signed test certificate in `testdata/` for localhost, 127.0.0.1 and ::1; `server.ClientTLS()` is a client config that trusts it.
  It plays with the lowest latency (`min_latency on`, `mw_latency 0`), so a player gets each message at once rather than in 350ms batches; a case that tests the default batching needs a variant.
  It serves every stream as HTTP-FLV at `/[app]/[stream].flv`, and as HLS (TS) at `/[app]/[stream].m3u8` and DASH at `/[app]/[stream].mpd`, both with 10s segments.
  WebRTC is on for the vhost, over UDP and TCP (`protocol all`), with its candidate at 127.0.0.1, so a session doesn't depend on the host's network interfaces; WHIP and WHEP are on the HTTP API port. The host of a WHIP or WHEP request is a candidate too (`api_as_candidates`, on by default), a name as it is, never resolved (`keep_api_domain on`, `resolve_api_domain off`), so no case depends on DNS. It doesn't convert between RTMP and WebRTC (`rtmp_to_rtc` and `rtc_to_rtmp` are off), which would transcode the audio of every stream on the shard's one thread.
  SRT is on for the vhost, with its streams converted to RTMP (`srt_to_rtmp`), and with no receive latency (`recvlatency 0`, which sets it, since SRS applies `latency` first and the `recvlatency` default of 120ms overrides it), so SRS passes on what an SRT publisher sends at once.
  RTSP is on for the vhost, so every RTMP stream plays over RTSP (`rtmp_to_rtsp`, on by default).
  It serves the files of its HTTP server's dir, `./objs/nginx/html` (`Server.WebRoot`), at every path nothing else mounts, and the default vhost's static files (`http_static`) of `./static/[vhost]` at `/static/` (`server.CommonStatic`, `server.WithStatic`); a case writes the files it asks for in a dir of its own.
  Every hook (`on_connect`, `on_close`, `on_publish`, `on_unpublish`, `on_play`, `on_stop`, `on_dvr`, `on_hls`, `on_hls_notify`) calls one mock at `/hooks/<action>`, `server.Common(c).Hooks`; `on_hls_notify` is a GET, with its action and every variable SRS fills in (`[server_id]`, `[service_id]`, `[app]`, `[stream]`, `[ts_url]`, `[param]`) in the query. It accepts every request unless a case scripts a reply, and a case scripts only its own stream, such as `Hooks.Script(mock.Match{Action: "on_publish", Stream: stream}, mock.Reject(403))`. A variant gets its own mock with `Config.Hooks`, and `Config.HookURLs` gives a hook several URLs, each a path on the mock such as `/more`, or `server.HookDown`, a port of the range nothing listens on. `Config.ForwardBackend` turns forward on with the mock as its backend, at `/api/v1/forward`: every publish then asks it for the URLs to forward to, as an `on_forward`, and a case scripts the answer, such as `Hooks.Script(mock.Match{Action: "on_forward", Stream: stream}, mock.JSON(...))`. `Config.Heartbeat` turns the heartbeat on, POSTing to the mock at `server.HeartbeatPath`, with its interval in whole seconds (SRS beats on its 1s timer), device id, ip (`SRS_DEVICE_IP`), summaries, ports, bearer token and a query on its URL; a case matches the heartbeats by that path.
- **Remux variants:** a vhost has one HTTP remux mount, so HTTP-TS, MP3 and AAC each have a variant, `TsMount`, `Mp3Mount` and `AacMount` (`server.RemuxConfig`), with RTMP, the HTTP API and server, and Common's latency. They are shared servers, with RTMPS too for the Convert groups, and `TsMount` also has WebRTC with `rtmp_to_rtc on` (`server.RTC{RTMPToRTC: true}`), which converts each RTMP stream to WebRTC and transcodes its AAC to Opus; Common keeps it off, since it would transcode the audio of every stream. All three have WebRTC with `rtc_to_rtmp on` (`server.RTC{RTCToRTMP: true}`) too, which converts each WebRTC stream to RTMP and transcodes its Opus to AAC; Common keeps it off, since it would transcode the audio of every WebRTC stream and refuse a WebRTC publish whose audio it can't transcode, such as G.711. `server.RemuxVariant` sets the remux settings Common keeps at their defaults (`guess_has_av`, `has_audio`, `has_video`, `drop_if_not_match`, `fast_cache`), the HTTP server's `crossdomain`, or turns the remux off: `NoGuess`, `NoAudio`, `NoVideoKeep` and `RemuxOff` for HTTP-FLV.
- **API variants:** `Config.APIAuth` turns the API's basic or bearer authentication on (`rtc_bearer_enabled` with `RTC`), and the adapter sends its credentials on its own requests; a config's `Env` may not set `SRS_HTTP_API_AUTH_*`. `Config.OneHTTPPort` puts the HTTP API on the HTTP server's port and the HTTPS API on the HTTPS server's, the one-port mode; Common has a port for each. `server.Start` fails with a `*server.ExitError` and its exit code when SRS exits before it is ready, such as for a config it refuses.
- **Security variants:** the security rules apply to every vhost, so each rule set has a server of its own, `server.WithSecurity`: the security on, and its allow and deny rules for publish and play, each a list of `all`, IPs and CIDRs. Every client of a case connects from 127.0.0.1, or ::1 over IPv6, so a rule set tells clients apart by protocol and by IP version only. SRS no longer has the referer check (`refer`), and refuses its config.
- **Forward topologies:** forward groups run in the timer process, since a forwarder sends what it queued once per receive timeout of its connection to the destination, 500ms, so a forwarded stream reaches its destination up to 500ms after it was sent; their cases that play nothing forwarded are Normal. Two destinations, `ForwardDest1` and `ForwardDest2`, are shared servers with RTMP, the API and hooks; `ForwardDest2` has forward off with `ForwardDest1` as its destination. `server.WithForward` sets a config's destinations, and forward on, or off with `Off`; with `Config.ForwardBackend` it sets only the destinations, which SRS ignores while a backend is set. A forwarder starts its destination at a keyframe that comes after it connected, so `publishForwarded` publishes, waits until every forward is forwarding, then sends the file. `Server.Restart` starts a stopped server again on the same ports, in the same directory, for a destination that goes away; a server with hooks can't restart, since its mock closes with it. The cases of `TestTimer_Forward_Retry` share one stop and start of their destination (`restartRound`), which happens once every case has reached it, or 2s after the first did; its destination and two origins are shared servers of its own, so they stop at the end with the others, at once, as each takes about a second to quit.
- **Edge topologies:** `server.WithEdge` makes a config an edge of every vhost, with its origins in order (an edge takes the next one when one fails), token traverse, and the protocol it pulls with, `flv` from an origin's HTTP server. The edge groups of a process share one origin, `EdgeOrigin`, with RTMP, HTTP-FLV and hooks; each edge has the same config plus its cluster settings. `server.DownAddr` is a port of the range nothing listens on, an origin that is down. An edge pulls a stream when its first player comes, and stops when its last one goes; it pushes a stream published to it to an origin, sending what it queued each time its connection to the origin reads a message or times out, 500ms, so the media a publisher sends before the push starts reaches the origin at once and the rest in batches. An edge waits 3s before it pulls again, so a case of a failed pull is a timer case.
- **Origin cluster topologies:** `server.WithOriginCluster` makes a config an origin of an origin cluster for every vhost, with the HTTP APIs of its coworkers in the order it asks them. The origins of a cluster know each other's API before they start, so a case reserves their API ports with `server.ReservePort` and gives each its `Config.APIPort`. A player of an origin that doesn't publish the stream gets NetStream.Play.Start, then an RTMP 302 redirect, a status of level error whose `ex` has the coworker's URL (`rtmp.Status.Ex`, read with `Client.WaitStatus`); SRS asks `/api/v1/clusters` with the query values as they are, not URL-encoded, so the cases ask the same way.
- **DVR variants:** DVR records every stream of every vhost, or those of `dvr_apply`, so each DVR config has a server of its own, `server.WithDVR`: the plan, the path of the files, its extension the format (`.flv` or `.mp4`), `dvr_duration` in seconds, `dvr_wait_keyframe` and `dvr_apply`, with RTMP, the HTTP API and hooks. The files go under `./dvr` in the server's directory, and a case reads each file at the path of its `on_dvr`, the `file` relative to the `cwd`. A case publishes its media at once and closes the publisher (`publishDvr`), which ends the session and its last file; it pauses 2ms before each keyframe, so each segment of a path with the time to the millisecond gets a name of its own, as SRS refuses to write a file that is there. `dvr_apply` names each stream before the server starts, so `TestDvr_Apply` lists the stream of each copy of its applied cases (`check.CopyNames`).
- **HTTP-FLV players on Common:** SRS tears down the HTTP mount of every unpublished stream on one shared worker, which polls every 100ms while the stream still has a player, and refuses to publish a stream whose old mount it is tearing down. So a player left at the unpublish can make another case's republish fail. A player from `httpFlvPlayer` waits on close, out of the case time, until SRS has dropped it, and a case that unpublishes with a player attached runs on a variant.
- **Play variants:** `server.PlayConfig` sets the play settings Common keeps at their defaults (`gop_cache`, `gop_cache_max_frames`, `queue_length`, `reduce_sequence_header`, `time_jitter`, `atc`, `mix_correct`, `send_min_interval`), or replaces its latency with `min_latency off` and merged writes and reads (`mw_latency`, `mw_msgs`, `mr`), with RTMP and the HTTP API: `GopCacheOff`, `GopCacheMaxFrames`, `ReduceSequenceHeader`, `JitterZero`, `JitterOff`, `AtcMixCorrect`, `MergedWrite`, `SendMinInterval`, and the timer groups `QueueDefault` and `QueueLength`. Settings that don't interfere share one variant, such as `atc` with `mix_correct`.
- **SRT players:** SRS keeps no GOP for SRT either, so a case connects its SRT player before the stream is published and waits for its `on_play` (`srtPlayer`); SRS makes the player's consumer right after the hook answers, before the publisher's own hooks. A caller SRS closes right after the handshake, such as one with a bad streamid or a second publisher, is dialed with a 250ms idle timeout and checked with `WaitClosedProbing` (`dialSRTEarlyClose`, `checkSRTClosedEarly`). The publisher (`startSRTPublisher`) sends the TS test file's first 500ms of PCR at once, then real time: ffmpeg's TS muxer sends the audio of a moment after its video, and the lead gets the player both sequence headers at once.
- **RTSP players:** SRS keeps no GOP for RTSP either, plays only over TCP, and describes a stream only once a publisher has sent the sequence headers that make its tracks. So `rtspPublisher` publishes the file's metadata and sequence headers over RTMP and holds the stream, the case plays (`rtspPlay` sends DESCRIBE again after a 404, for at most 300ms), then the publisher sends the media from its first keyframe, 200ms of it at once, then real time. SRS makes a player's consumer right after it answers PLAY, before it reads anything else.
- **GB28181 publishers:** a case plays the external SIP server and the device: it asks for a session by the publish API, connects to the GB port, and sends the test file from its first keyframe as PS over RTP over TCP; SRS publishes it to its own RTMP as `live/<id>`. SRS holds 2 video and 2 audio frames, and the last PS pack until the next one comes, before it sends any to RTMP, so a publisher sends 200ms at once, then real time (`gbStream.lead`), or 400ms at once when it sends no more (`gbBurst`). Each case has an SSRC of its own (`gbSSRC`). A known bug of `TestGb_Reconnect` crashes SRS, so that group has a server of its own (`crashServer`), whose exit is not checked: 33 processes in the suite.
- **WebRTC players:** SRS keeps no GOP for WebRTC, and it subscribes a player after the player's DTLS handshake, on a coroutine of its own, dropping what the publisher sends before. So a case connects its players before the publisher sends, and `sendRTC` has each player ask for a keyframe (a PLI) and waits until SRS forwards the request to the publisher, which shows the player is subscribed; then it sends the file from its first keyframe, the first 200ms at once.
- **Publish variants:** `server.PublishConfig` sets the publish timeouts Common keeps at their defaults (`firstpkt_timeout`, `normal_timeout`, `kickoff_for_idle`), with RTMP, the HTTP API and Common's latency: the shared timer server `PublishTimeout`, which `TestTimer_Heartbeat_Defaults` shares for the heartbeat every 1s at SRS's defaults. SRS checks a publisher once per timeout, so `kickoff_for_idle` acts only on those checks and shares the variant with the short timeouts.
- **HLS variants:** `server.HLSConfig` sets the HLS settings Common keeps at their defaults (`hls_fragment`, `hls_window`, `hls_td_ratio`, `hls_aof_ratio`, `hls_path` with the HTTP server's dir, `hls_m3u8_file`, `hls_ts_file`, `hls_entry_prefix`, `hls_ts_floor`, `hls_use_fmp4`, `hls_fmp4_file`, `hls_init_file`, `hls_keys`, `hls_fragments_per_key`, `hls_key_url`, `hls_ctx`, `hls_ts_ctx`, `hls_master_m3u8_path_relative`, `hls_dispose`, `hls_cleanup`), with RTMP, the HTTP API and server, and Common's latency, and no HTTP remux: `Options`; `TsFloor`, because `hls_ts_floor` changes when segments are cut, shared with the keys and session settings; `Fmp4`, since fmp4 changes the muxer; and `Fmp4Keys`, fmp4 with keys and `hls_ctx` off. `server.WithHLS` turns HLS on in another variant's config, with its HTTP server, like `server.WithDASH`. On Common, HLS cases publish only the segments they need (`publishThrough`), since every burst shares a shard's one thread with the real-time cases.
- **Command runs:** a case that runs the binary as a command, such as `-v`, `-h` or the config test `-t`, uses `server.Exec`: a dir of its own, the adapter's process settings and every listener off (`server.CLIEnv`), then the case's env, which may set any `SRS_*` value, a bad one too; it waits for the exit up to a timeout and kills a process that still runs, which started as a server. At most 4 runs go at once, and each starts, out of the case time, only while the process runs fewer SRS than its peak so far (waiting at most 2s), so the runs, each an SRS process, never raise the peak its servers set. The config test's output is SRS's log, so its cases check only the exit code (the black-box rule: no log text decides a case).
- **Process settings:** the adapter's process settings are fixed for every server: in the foreground, the log to the console it captures, a pid file in the server's dir, and the host's time zone. `Config.Process` replaces one of them (`SRS_PID`, `SRS_LOG_TANK`), `Config.ListenAlias` sets RTMP's port by `SRS_LISTEN`, `Config.WorkDir` makes a dir in the server's dir for `SRS_WORK_DIR` (`Server.WorkDir`), and `Config.TZ` sets `TZ`, for the cases of those settings, `TestEnv_Global`. `Config.BelowPeak` starts a server, like a command run, only while the process runs fewer SRS than its peak so far, for a group that would otherwise raise it. A command run may set `TZ` too, and `CLIRun.Dir` is its dir, for the files it wrote.
- **Variant:** a server only when Common can't do it: a value Common can't have, global state, a process change, or a topology. A variant group is one top-level test that starts its SRS, runs its cases as parallel subtests, and stops the SRS.
- **DASH variants:** `server.WithDASH` turns DASH on in another variant's config, with the DASH settings Common keeps at their defaults (`dash_fragment`, `dash_window_size`, `dash_path`, `dash_mpd_file`, `dash_dispose`, `dash_cleanup`), so DASH groups run on the shared servers `RemuxOff`, `Fmp4Keys`, `SegmentsDispose` and `SegmentsKeep`, whose groups publish little, rather than on servers of their own. `dash_path` doesn't change the HTTP server's dir, so a `dash_path` under it is served by its subdir (`./objs/nginx/html/dash` as `/dash`). DASH segments are fmp4 files in a dir per stream beside the MPD, so they don't meet the HLS files.
- **Shared variants:** when one config serves the groups of several features, they share one server with `server.Shared(t, name, cfg)`: the first group that asks starts it, every other must ask with the same config, and it stops after every test, like Common. Each group still has its own name. `TestHttpFlv_RemuxOff`, `TestHls_Fmp4Default`, `TestDash_Options`, `TestSrt_Latencies` and `TestRtsp_Options` share `RemuxOff`: the HTTP remux off, HLS in fmp4 at SRS's defaults, the DASH settings of `TestDash_Options`, SRT with `recvlatency 250` and `peerlatency 150`, and RTSP with `rtmp_to_rtsp off` (`server.WithRTSP`); `TestApi_RawApi` shares it too, for the RAW API on with reload off (`server.WithRawAPI`), and `TestHttpStatic_RemuxOff`, for FLV files with the remux off. `TestHls_TsFloor`, `TestHls_Keys`, `TestHls_Sessions`, `TestRtc_NackTwccOff` and `TestSrt_Options` share `TsFloor`: `hls_ts_floor`, AES-128 keys with `hls_key_url` on the CDN host, `hls_ts_ctx off`, `hls_master_m3u8_path_relative on`, hooks, WebRTC over UDP with `nack off` and `twcc off`, and SRT (`server.WithSRT`) for `TestSrt_Options`, with `default_mode publish`, `default_app srtapp`, `default_streamid #!::r=srtapp/default,m=request` and a passphrase. `TestHls_Fmp4Keys`, `TestHls_CtxOff`, `TestDash_StreamDir`, `TestRtc_Transport`, `TestRtc_PreferRtx`, `TestSrt_LatencyOnly`, `TestRtsp_VhostOff` and `TestHttpStatic_CtxOff` share `Fmp4Keys`: fmp4 with keys at the default `hls_key_url`, `hls_ctx off`, hooks, DASH with 2s fragments and the MPD in a dir per stream, and WebRTC over UDP only with `dtls_role active`, `stun_strict_check on`, `api_as_candidates off` and `nack_prefer_rtx on` (`server.WithRTC`), SRT with `latency 300` alone, and the RTSP listener with RTSP off on the vhost, and static HLS with `hls_ctx off`. `TestHttpTs_TsMount` and `TestConvert_TsMount` share `TsMount`, `TestHttpAudio_Mp3Mount` and `TestConvert_Mp3Mount` share `Mp3Mount`, `TestHttpAudio_AacMount` and `TestConvert_AacMount` share `AacMount`, and `TestHls_Fmp4` has `Fmp4`, each with RTMPS, and WebRTC with `rtc_to_rtmp` for the WebRTC cells; `TestConvert_Fmp4` runs a server of `Fmp4`'s config of its own, since one server for both was too busy. `TestConvert_RtcToRtmp` has `RtcToRtmp` (`sharedRtcToRtmp`) for itself, named so later conversion groups can share it: WebRTC with `rtc_to_rtmp`, HTTP-FLV with `guess_has_av off`, HLS and DASH with 1s fragments, SRT, RTSP and hooks. `TestConvert_GbSegments` has `GbSegments` (`sharedGbSegmentsConfig`) for itself: the GB28181 caster, and HLS and DASH with 1s fragments. In the timer process, `TestTimer_Rtmp_QueueDefault`, `TestTimer_Hls_Dispose` and `TestTimer_Dash_Dispose` share `SegmentsDispose`: the default play queue, and HLS and DASH with 1s fragments and `hls_dispose` and `dash_dispose` at 0.5s (SRS reads a fraction of a second, but checks its sources only every 3s). `TestTimer_Rtmp_QueueLength`, `TestTimer_Hls_Cleanup`, `TestTimer_Dash_Cleanup`, `TestTimer_Hls_Sessions`, `TestTimer_Srt_PeerIdle`, `TestTimer_Gb_MediaTimeout`, `TestTimer_Convert_Reports`, `TestTimer_Reload_RawApi`, `TestTimer_Reload_Sighup`, `TestTimer_Signal_Console` and `TestTimer_Heartbeat_Full` share `SegmentsKeep`: a 1s play queue, HLS with 1s fragments, `hls_window 0.5` (sessions end after 1s without a request) and `hls_cleanup off`, DASH with 1s fragments and `dash_cleanup off`, and hooks, SRT with `peer_idle_timeout 1000`, and the GB28181 caster with `media_connect_timeout 1` (`server.WithGB`), WebRTC over UDP, and the RAW API with reload allowed, whose reloads, by the API or SIGHUP, fail without a config file and change nothing, and SIGUSR1, which reopens no log on the console, and the heartbeat every 1s with every setting on, which the other groups never read.
- **Bursts:** SRS runs on one thread and shares it fairly, so many cases that send a burst at once, such as a whole file without pacing, make each of them, and the real-time cases beside them, as slow as all of them together. A case holds one of a server's 2 burst slots while it sends one (`srs.Burst(c)`); the wait for a slot is not part of its time. `publishAll` does it for the segment groups.
- **Hook mock:** it closes each connection after its reply, so SRS, which opens one per hook, leaves no socket in TIME_WAIT on an ephemeral port; a run of 1,000 cases would otherwise use them up.

### Classes

Each case declares its class first, through the case helper in
`internal/check`, and runs as a parallel subtest of its group:

```go
check.Case(t, "PlayBeforePublish", check.Normal, func(c *check.C) {
	srs := server.Common(c)
	c.Must(err, "connect")              // Fails and stops the case.
	c.CheckEqual(got, want, "frames")   // Fails and goes on.
})
```

A case checks only through `c` (`c.Check...`, `c.Must`, `c.Errorf`,
`c.Fatalf`), never through the group's `t`, so the helper decides the result.
A case over its limit fails with `too slow: <ms> > <limit>`. Time is measured
inside the case, without a server start (`server.Common` and `server.Group`)
and without its cleanups.

| Class | Limit | Cases |
|---|---|---|
| Fast | ≤100ms | API, hooks, security, static files, a play that gets its first frames from the GOP cache |
| Normal | ≤500ms | Most streaming cases, WebRTC and SRT handshakes, segment groups, edge and forward chains |
| Timer | ≤10s, only in `TestTimer_*` groups | Cases that wait on a whole-second SRS timer or a 1s tick, with every timeout at its smallest value |

### Real time

Streams are published in real time, like ffmpeg `-re`. Segment groups (HLS,
DASH and DVR) publish without `-re`, because segments follow media timestamps,
not wall time. Their players fetch whole segments, so a report can go a
little past the stop condition.

### Stream checks

A case checks a stream with the suite's own analyzers, never ffprobe. They
fill one stream report (`internal/report`): codecs, picture size, sample
rate, sequence headers, keyframes and frames, timestamps that only go forward
without gaps, the frames out of time order across the two tracks
(`Unordered`), and the A/V sync difference. TS and raw AAC carry the sequence
headers in band, before each keyframe or in each frame, so their report counts
one each time they first appear or change. The case states when to stop, as a
`report.Until` such as "both sequence headers, 1 keyframe, 5 video frames", so
the analyzer stops as soon as the check can pass:

```go
r, err := flv.PlayHTTP(ctx, nil, url, report.Until{VideoHeader: true, AudioHeader: true, Keyframes: 1, VideoFrames: 5})
c.Must(err, "play") // On a timeout, the error has what it waited for and what it got.
c.CheckNoError(r.CheckTimestamps(100*time.Millisecond), "timestamps")
```

- **Unavailable:** a recipe whose encoder the ffmpeg lacks, such as VP9 and AV1 in CI, is recorded as unavailable, and its cases skip with "ffmpeg lacks <encoder>".

- **Cache:** `testdata/media/manifest.json` records the source's size and SHA-256, each recipe and the ffmpeg version. Only a file whose entry changed is made again.

- **Checks:** ffmpeg versions make different bytes, so nothing checks bytes. The unit tests of `internal/media`, which need `make integ-prepare` first, read each file and check its codecs, profile, B-frames, GOP, frame rate, sample rate, duration and frame counts.

### Known bugs

A case that finds an SRS bug is marked `KnownBug(c, "<reason>")`, not fixed or
skipped. It still runs: a failure passes and logs `KNOWN BUG: <reason>`, and a
pass fails with "bug fixed, remove the KnownBug mark".
`-integ.known-bugs=fail` makes them fail like normal cases.
A bug that shows only on some systems, in a race, or with some test media is
marked only when the case sees it, such as the Linux-only ones.

### Ports

The suite owns ports 14000–14999: the main process allocates from 14000–14799
and the timer process from 14800–14999. `SRS_INTEG_PORTS` moves or widens the
range. A server gets a port only for each listener it turns on, and one for
its hook mock when it has one, never an SRS default port, and a port is never
handed out twice in a run. When the range runs out, the run fails with "port
range exhausted, widen SRS_INTEG_PORTS".

## Conversion matrix

Each publish protocol, each play protocol, and each codec of the test media
the pair carries: one case per cell, `TestConvert_<Group>/<Source>To<Player>_<Codec>`,
such as `TestConvert_Common/RtmpToHlsTs_HevcAac` (`cases/convert_test.go`, and
`cases/convert_rtc_test.go` for WebRTC, `cases/convert_srt_test.go` for SRT
and `cases/convert_gb_test.go` for GB28181 as the source, and
`cases/convert_codec_test.go` for the codec paths).
A cell plays the stream it publishes, and the player's report must match the
media: the codecs below, the source's 768x320 from a keyframe with one
sequence header, AAC and MP3 at 44.1 kHz stereo and Opus at 48 kHz stereo,
AAC with one sequence header, timestamps that only go forward without gaps,
and A/V sync. Or SRS refuses the player, or the cell says what it gets.
Each pair's result comes from the SRS docs and code.

- **Codecs:** `H264Aac` (H.264 High with AAC; H.264 Baseline for WebRTC and RTSP), `HevcAac` (HEVC over enhanced RTMP), `H264Mp3`, `AacOnly` and `H264Only` (H.264 High).
- **RTMPS** is RTMP over TLS into the same stream, so it has one cell per player, with the first codec the player carries; the codec paths are those of RTMP.
- **Players:** RTMP and HTTP-FLV join a real-time stream 200ms in, from the GOP cache; HTTP-TS, MP3 and AAC too, the audio mounts from the next frame; HLS and DASH play a stream published at once (no `-re`); RTSP and WebRTC players connect before the media, since SRS keeps no GOP for them.

- **Codecs:** `H264Aac` (the H.264 Baseline and AAC test file, without B-frames, since SRS takes each frame's DTS as its PTS), `HevcAac` (the HEVC and AAC test file), and `H264Only` (the video of the H.264 one, as a device with its audio off sends it). SRS takes AAC only from PS, and a device sends no audio without video, so there is no audio-only cell. The case is the device: it asks for a session by the publish API and sends PS over RTP over TCP from the first keyframe (`cases/convert_gb_test.go`); SRS publishes it to its own RTMP as `live/<id>`, so every RTMP player and remux plays it, and RTSP and WebRTC with `rtmp_to_rtsp` and `rtmp_to_rtc` as for an RTMP stream.
- **What SRS holds:** SRS holds the last PS pack until the next one comes, and sends a frame on only while it holds 2 video and 2 audio frames, or, with no audio, more than 100 video frames. So a real-time publisher with no audio sends 4s more at once, and a segment publisher sends 200ms more (4.2s with no audio). SRS stamps the first keyframe 1ms after the sequence header of the same time, so the first 1s HLS segment lasts 999ms at the keyframe at 1s and ends only at the next one. `GbToRtmp_LatencyH264Only` (a known bug) shows the 4s a real-time stream with no audio is held.
- **RTSP:** SRS keeps no GOP for RTSP, so the device sends its first GOP and the next keyframe at once, which SRS holds as its oldest video frame (with the audio of the next 100ms, or with the next 100 video frames), the player joins, and the rest comes in real time: the player's first frame is that keyframe.
- **Groups:** RTMP, HTTP-FLV, RTSP, SRT not converted and WHEP refused on `Common`; HLS ts and DASH, with 1s fragments, on the new shared `GbSegments`, since a GB stream costs SRS more than an RTMP one (it reads the PS and publishes it again over RTMP): Common's 10s segments would take 10 times the media, and on `RtcToRtmp`, which has 1s fragments, the GB bursts beside its Opus transcoding made cells of both too slow; HTTP-TS and WHEP on `TsMount`; HTTP MP3 on `Mp3Mount`; HTTP AAC on `AacMount`; HLS fmp4 on `Fmp4`. Those 4 now have the GB28181 caster too. A segment publisher sends with a 32 KB send buffer, so it holds its burst slot until SRS has read most of the burst.
- **SRT and WHEP:** SRS converts no RTMP stream to SRT, so an SRT player of a GB stream gets nothing (`GbToSrt_NotConverted`). With `rtmp_to_rtc` off, a WHEP player is refused, 500 `RtcDisabled` (`GbToWhep_Disabled`); `TsMount` turns it on, and SRS transcodes AAC to Opus, HEVC too from its legacy tags.
- **Known bugs:** RTMP and HTTP-FLV of HEVC (legacy FLV tags, codec id 12, not enhanced RTMP); HLS fmp4 of a stream with video and audio (the AAC sequence header comes after the first video frame, 1ms after it here); DASH of a stream with no audio (no MPD); the 4s SRS holds of a stream with no audio.
